## О проекте

Система управления для онлайн-магазина ювелирных изделий и бижутерии (кольца, серьги, бусы и т.д.). Владелец магазина сейчас ведёт учёт вручную в тетради; система должна объединить: товары, склад, заказы, доставку, расходы, финансы и отчёты в одном месте.

Полное техническое задание: `docs/TZ.md` (перевод на русский, оригинал на узбекском). **Всегда сверяйся с ТЗ при реализации бизнес-логики** — там точные формулы расчёта себестоимости, правила статусов заказа и т.д.

Основной поток данных: **Товар → Приход → Склад → Заказ/Продажа → Расход → Выручка → Прибыль → Отчёт**

## Критичные бизнес-правила (из ТЗ, раздел 23)

Эти правила нельзя нарушать ни при каком рефакторинге — при любой задаче, касающейся склада или заказов, перечитывай их:

1. **Остаток не может уйти в минус.** Продажа сверх остатка блокируется на уровне сервиса (`InventoryService`) до записи в БД, с понятной ошибкой пользователю.
2. **Каждое изменение остатка логируется.** Любая операция (приход, продажа, возврат, корректировка) создаёт запись в `StockMovement`. Никаких прямых `update` количества в обход этого лога.
3. **Исторические заказы неизменны.** Изменение цены товара не влияет на уже созданные заказы — цена копируется в `OrderItem.priceAtSale` в момент создания заказа.
4. **Себестоимость фиксируется на момент продажи.** `OrderItem.costAtSale` — снапшот текущей средней себестоимости варианта товара, не ссылка.
5. **Заказ не должен учитываться дважды.** Списание остатка происходит один раз — при переходе в статус `SHIPPED`. Повторные обновления статуса не должны повторно триггерить списание/начисление выручки. Используй проверку текущего статуса перед сменой + транзакции Prisma (`$transaction`).
6. **Отмена возвращает остаток.** Если заказ был в статусе `SHIPPED` или позже и переходит в `CANCELLED`, товар возвращается на склад, заказ исключается из выручки/прибыли.
7. **Доставка считается отдельно.** Доставка, оплаченная клиентом, не входит в выручку товара и не является прибылью. Доставка, оплаченная магазином, — это расход (`storeDeliveryCost`), вычитаемый при расчёте чистой прибыли.

### Формула себестоимости (moving average)

При каждом приходе пересчитывается средневзвешенная себестоимость варианта:

```
новая_средняя = (текущий_остаток × текущая_себестоимость + новое_количество × новая_цена_прихода) / (текущий_остаток + новое_количество)
```

Цена упаковки/доп. расходов, если общая на партию, делится на количество товаров в приходе и добавляется к цене за единицу до пересчёта средней.

### Статусы заказа и их эффект на склад/финансы

| Статус      | Списание со склада                 | Учёт в выручке/прибыли |
| ----------- | ---------------------------------- | ---------------------- |
| `NEW`       | нет                                | нет                    |
| `CONFIRMED` | нет                                | нет                    |
| `SHIPPED`   | да (в этот момент)                 | нет                    |
| `DELIVERED` | уже списано                        | да                     |
| `CANCELLED` | возврат остатка, если было списано | нет                    |

## Соглашения по коду

**Backend (NestJS):**

- Один модуль = одна доменная область (products, orders, inventory...), со своими `*.controller.ts`, `*.service.ts`, `*.module.ts`, `dto/`. Все бизнес-модули живут в `src/modules/<domain>/`.
- Авторизация — JWT (модуль `src/modules/auth`), логин по номеру телефона (не email). Роли: `OWNER` (полный доступ), `MANAGER` (без финансов/настроек). Все роуты защищены глобальным `JwtAuthGuard` по умолчанию; публичные — помечать `@Public()`. Ролевые ограничения — `@Roles()` + `RolesGuard` точечно на нужных эндпоинтах. Новых пользователей создаёт только `OWNER` через `POST /auth/register`; самый первый `OWNER` (и опционально тестовый `MANAGER`) создаётся через `npm run seed` (переменные `SEED_OWNER_*` / `SEED_MANAGER_*` в `.env`).
- Переменные окружения — только через типизированный `src/config/env.ts`, не через `process.env` напрямую и не через `@nestjs/config`.
- Вся бизнес-логика — в сервисах, не в контроллерах.
- Любая операция, меняющая остаток и создающая заказ/движение одновременно, — внутри `prisma.$transaction`.
- DTO валидируются через `class-validator`; никаких `any` в публичных методах сервисов.
- Денежные суммы храним как `Int` (в тийинах/минимальных единицах валюты), не `Float` — избегаем ошибок округления.

**Frontend (React):**

- Данные с сервера — только через TanStack Query хуки в `src/api/`, не напрямую `fetch` в компонентах.
- Формы — React Hook Form + Zod-схема, схему держим рядом с формой.
- Общий UI — из `shadcn/ui`, кастомные компоненты — в `src/components/ui` только если аналога в shadcn нет.
- Фильтр периода на дашборде — глобальный Zustand-store (`src/store/dateFilter.ts`), чтобы все виджеты дашборда подписывались на один источник.

**Общее:**

- Именование БД/Prisma-моделей — camelCase в TS, Prisma сам мапит в snake_case для Postgres (`@@map`).
- Коммиты — Conventional Commits (`feat:`, `fix:`, `refactor:`, `chore:`).
- Не коммитить `.env` файлы — только `.env.example`.

## Что не нужно делать

- Не использовать `Float`/`Double` для денег.
- Не писать прямые SQL-запросы в обход Prisma без явной причины.
- Не делать глобальный стейт для данных, которые можно получить через React Query (кеш запросов — не дублировать в Zustand).
- Не менять уже завершённые (`DELIVERED`/`CANCELLED`) заказы — только чтение истории.
